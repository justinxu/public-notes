XXL-JOB 在 Consul Service Mesh 中的分片调度方案

摘要

问题背景是XXL-JOB 的分片广播依赖调度中心能看到多个执行器实例地址；如果执行器只注册一个 Kubernetes Service 或 Mesh 服务名，XXL-JOB Admin 只能看到一个逻辑地址，SHARDING_BROADCAST、FAILOVER、BUSYOVER、ROUND、RANDOM、CONSISTENT_HASH 等实例级路由能力都会退化。

方案收敛为三种模式：普通任务走 ServiceName；XXL-JOB 原生分片走 Pod 级注册；核心批处理走独立任务编排服务。

官方依据

  • XXL-JOB 官方文档说明：执行器支持自动注册，调度中心可以发现注册任务并触发执行；执行器集群部署时支持多种路由策略，包括分片广播；分片广播会对执行器集群中的实例广播执行，并基于分片参数开发任务逻辑。参考：XXL-JOB 官方文档 与 English Documentation。
  • XXL-JOB 执行器配置中，xxl.job.executor.address 为空时使用内嵌服务 IP:PORT 注册；不为空时优先使用该配置作为注册地址。参考：执行器配置说明。
  • Consul 官方文档说明：Consul Service Mesh 使用基于 SPIFFE X.509 标准的证书做服务身份和 mTLS；透明代理会把 Pod 的入站/出站流量重定向到 sidecar proxy；在 Kubernetes 中启用透明代理需要 consul.hashicorp.com/connect-inject 与 consul.hashicorp.com/transparent-proxy 等配置，并通过 Service Intentions 显式允许服务间通信。参考：Consul service mesh、Enable transparent proxy mode on Kubernetes、Consul on Kubernetes annotations。

关于 Pod IP 直连与 mTLS

原草稿中“Pod IP 直连也能完美享受 mTLS”的判断需要加前提。更准确的说法是：

当 Admin 与 Executor 都被 Consul Connect 注入、透明代理生效、执行器端口被 Consul service 正确注册、Intentions 允许访问、且流量没有被排除出 transparent proxy 时，应用层访问 PodIP:9999 可以被本地 sidecar 拦截并转换为 Envoy 间 mTLS 流量。

mTLS 证书绑定的是服务身份，不是 Pod IP 本身。Consul 使用 SPIFFE X.509 证书表达服务身份，Envoy 之间完成双向证书校验和加密连接，Intentions 再按源服务与目标服务授权。

因此不能只凭“代码里访问的是 Pod IP”判断是否有 mTLS。必须验证流量是否真正经过 sidecar。

需要检查：

  • Pod 上存在 consul-dataplane 或 Envoy sidecar。
  • Pod 注解包含 consul.hashicorp.com/connect-inject: "true"。
  • transparent proxy 对该 Pod 生效。
  • 没有用 transparent-proxy-exclude-inbound-ports 或 transparent-proxy-exclude-outbound-ports 排除 9999。
  • xxl-job-admin 到 xxl-job-executor 的 Intentions 是 allow。
  • NetworkPolicy 允许 sidecar 和应用端口所需通信。

Headless Service 方案

Headless Service 可以用于实例级 DNS 发现：

但要注意：

  • 普通 Deployment 的 Pod 名称不稳定，不适合作为长期实例身份。
  • Headless Service 返回多个 endpoint，并不代表 XXL-JOB Admin 会自动把这些 endpoint 当作多个执行器地址。
  • 如果要让 XXL-JOB 看到多个地址，仍然需要执行器逐个注册，或额外实现 endpoint 同步器，把 endpoint 列表同步到 XXL-JOB 执行器地址列表。
  • 如果要稳定实例名，可以使用 StatefulSet，让地址类似 xxl-job-executor-0.xxl-job-executor-headless.default.svc.cluster.local:9999。

对 XXL-JOB 原生分片来说，最直接稳定的方式仍是执行器 Pod 自注册。

生命周期与脏地址治理

Pod 级注册的风险在生命周期：

治理要求：

  • readiness 通过前不要对外接任务。
  • 停止前给执行中任务留出收尾时间。
  • preStop 与 terminationGracePeriodSeconds 覆盖最长安全下线窗口。
  • 依赖 XXL-JOB 心跳剔除失效实例，同时监控注册表中旧地址滞留时间。
  • 任务必须幂等，按 jobId + triggerTime + shardIndex 或业务唯一键做重复保护。
  • 长任务需要 checkpoint，不能只依赖进程内状态。

模式三：XXL-JOB 只做触发，任务服务内部编排

对核心批处理、长任务、财务对账、库存重算、履约补偿等任务，不建议把全部分布式执行语义压在 XXL-JOB 的实例路由上。

更稳的长期架构是：

任务分片可以由这些机制承担：

  • 数据库分片表 + 乐观锁
  • Redis/Consul lock
  • Kafka/Pulsar 分区
  • Kubernetes Job
  • Argo Workflows
  • 内部任务状态机

这种模式下，XXL-JOB 只需要调用一个服务名。Mesh 隐藏后端实例不是问题，因为真正的分片、锁、状态、重试都在任务服务内部完成。

推荐标准

任务等级调度方式注册方式适用场景
L1 Trigger JobXXL-JOB 触发一次ServiceName普通巡检、缓存清理、轻量同步
L2 Sharding JobXXL-JOB 分片广播Pod 级注册批量扫描、消息重推、可并行补偿
L3 Orchestrated JobXXL-JOB 只触发任务服务ServiceName核心长任务、可恢复批处理、财务/库存/履约类任务

默认选择：

  • 普通任务：ServiceName + Mesh LB。
  • 依赖 XXL-JOB 原生分片：PodIP 或稳定实例 DNS 注册。
  • 核心批处理：独立 Task Service 编排。

验收清单

分片模式上线前至少验证：

  • XXL-JOB Admin 的执行器列表中能看到多个不同的 executor address。
  • 新建任务选择 SHARDING_BROADCAST 后，每个执行器 Pod 都能收到一次调度。
  • 每个 Pod 日志能打印不同的 shardIndex，且 shardTotal 等于当前可用执行器数。
  • 扩容后，下一轮调度能看到新的 shardTotal。
  • 滚动升级期间，旧 Pod 不再接收新任务，正在执行的任务能完成或被幂等重试。
  • kill、log、callback 行为能命中正确实例，或已接受其限制。
  • Consul sidecar 日志和 Envoy 配置能证明流量经过 Mesh。
  • Intentions、NetworkPolicy、readiness、preStop、terminationGracePeriodSeconds 均已配置。
  • 任务侧有重复触发保护和失败补偿策略。

最终判断

  1. 不需要分片的任务，注册 ServiceName，接受 XXL-JOB 实例级能力退化。
  2. 需要 XXL-JOB 原生分片广播的任务，执行器必须以 Pod 级地址或稳定实例地址注册，让 Admin 看到多个 executor address。
  3. 核心批处理和长任务，不把 XXL-JOB 当分布式执行引擎，而是让它只触发任务编排服务。
  4. Consul Mesh 下的 Pod IP 直连 mTLS 必须实测确认，不能用“访问 Pod IP”或“注入 sidecar”单点推断。
